## 1. React Server Components (RSC) vs. Client Components

### 1.1 Architecture & Render Trees
In Next.js App Router, the default rendering paradigm is **React Server Components (RSC)**. RSCs execute exclusively on the server and send serialized UI to the client, effectively reducing the JavaScript bundle size and mitigating client-side processing overhead.
- **Server Components (e.g., `layout.tsx`, `page.tsx`)**: Handle data fetching securely without exposing secrets, and do not ship React hooks (like `useState`, `useEffect`) to the client.
- **Client Components (e.g., `product-form.tsx`, `cart.tsx`, `theme-toggle.tsx`)**: Denoted by the `'use client'` directive. These components hydrate on the browser to provide interactivity.

### 1.2 Hydration Optimization Strategies
Hydration occurs when React attaches event listeners to the static HTML generated by the server. A **hydration mismatch** happens when the server-rendered HTML differs from the initial client render (e.g., trying to access `localStorage` or `window` on the server).

**Strategies Implemented:**
1. **Suppressing Hydration Warnings:** The `next-themes` setup modifies the `<html>` tag class for dark mode dynamically. We pass `suppressHydrationWarning` to the `<html>` tag to prevent React from throwing errors due to the server not knowing the user's system theme preference.
2. **Safe Hydration Hooks:** For the Zustand store (which uses `localStorage`), rendering local storage data on the server causes a mismatch because the server's state is empty. We circumvented this by creating a custom hook (`useStore.ts`) that delays rendering the persistent data until the component mounts (`useEffect`), ensuring the server and initial client render align perfectly.

## 2. Server State Handling vs. Zustand Client Caching

### 2.1 Server State (Next.js Server Actions)
Our application uses a Server Action (`createProductAction`) to handle mutations safely without needing a dedicated API route.
- **Security:** Business logic runs on the backend. We share a `Zod` validation schema (`schema.ts`) to enforce payload sanitization before saving to a database.
- **Optimistic UI:** When the form is submitted via `useTransition`, we prevent layout-blocking operations. We immediately display a loading state and dispatch success/error toasts depending on the action's response.

### 2.2 Client State Caching (Zustand)
While Server Actions manage remote data, we need localized state for UI responsiveness. We implemented **Zustand**, a lightweight atomic state manager, for the shopping cart.
- **Persistence:** Zustand's `persist` middleware automatically saves the cart state to `localStorage`.
- **Atomic Selectors:** By using selectors (e.g., `const items = useStore(useCartStore, (state) => state.items)`), we prevent unnecessary re-renders in nested layout boundaries. A change to the cart's total price only re-renders components explicitly subscribing to the price state, not the entire page.

## 3. Web Vitals & Lighthouse Audit Metrics

The application was built following modern web engineering practices to score optimally on Core Web Vitals:

- **Largest Contentful Paint (LCP):** By utilizing Server Components, our initial HTML is loaded extremely fast, keeping LCP low. Tailwind CSS eliminates render-blocking stylesheets.
- **Cumulative Layout Shift (CLS):** `next-themes` minimizes layout shifts during theme toggles. Additionally, the fallback loading skeletons provided in the `Cart` component (`animate-pulse`) reserve UI space, ensuring dynamic client data doesn't push elements down the page.
- **Interaction to Next Paint (INP):** Leveraging Radix UI primitives guarantees highly responsive and accessible UI elements. The form submission uses `useTransition` to yield to high-priority user interactions (like typing in inputs) while the Server Action executes in the background.
